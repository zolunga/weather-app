# Weather App

Full-stack Weather App with a NestJS backend and a React + Vite + TypeScript frontend.

The frontend talks only to the backend API. OpenWeather credentials stay on the backend and are never exposed in browser code.

## Structure

```text
weather-app/
  backend/   # NestJS API, OpenWeather integration, weather insights
  frontend/  # React + Vite app
  README.md
```

## Features

- Search weather by city or place.
- Switch units between metric and imperial in the frontend.
- Display current weather, forecast, and business insights from the backend.
- Weather condition icons for sunny, cloudy, rainy, stormy, snowy, foggy, and windy conditions.
- Loading, empty, and user-friendly error states.
- Swagger documentation for backend API exploration.
- CORS configured for local frontend origins.
- Vitest coverage for backend and frontend.

## Requirements

- Node.js 20 or newer
- npm
- OpenWeatherMap API key
- Docker and Docker Compose, if running the full app in containers

## Docker Setup

Create `backend/.env` from `backend/.env.example` and set your **OpenWeatherMap API key**.

```bash
cd backend
cp .env.example .env
```

Then start both services from the repository root:

```bash
docker compose up --build
```

The frontend runs at:

```text
http://localhost:3000
```

The backend API runs at:

```text
http://localhost:8000
```

Swagger UI is available at:

```text
http://localhost:8000/docs
```

## Backend Setup

```bash
cd backend
npm install
cp .env.example .env
```

Update `backend/.env`:

```bash
PORT=3000
CORS_ORIGIN=http://localhost:5173,http://127.0.0.1:5173
OPENWEATHER_API_KEY=your-openweathermap-api-key
OPENWEATHER_BASE_URL=https://api.openweathermap.org
WEATHER_CACHE_TTL_SECONDS=600
```

Run the backend:

```bash
npm run start:dev
```

The API runs on `http://localhost:3000`.

Swagger UI is available at:

```text
http://localhost:3000/docs
```

## Frontend Setup

```bash
cd frontend
npm install
```

## API Endpoints

- `GET /health`
- `GET /weather/current?location=Atlanta&units=metric`
- `GET /weather/forecast?location=Atlanta&units=metric`
- `GET /docs`

Backend environment variables:

| Variable | Description |
| --- | --- |
| `PORT` | HTTP port for the NestJS server |
| `CORS_ORIGIN` | Comma-separated frontend origins allowed by CORS |
| `OPENWEATHER_API_KEY` | OpenWeatherMap API key |
| `OPENWEATHER_BASE_URL` | OpenWeatherMap base URL, usually `https://api.openweathermap.org` |
| `WEATHER_CACHE_TTL_SECONDS` | In-memory weather cache TTL in seconds. Defaults to `600` |

Weather query params:

| Query param | Required | Values | Default |
| --- | --- | --- | --- |
| `location` | Yes | Any OpenWeatherMap-supported location text | none |
| `units` | No | `metric`, `imperial`, `standard` | `metric` |

## Architecture

The application follows a backend-for-frontend style architecture.

- React frontend consumes only the NestJS backend.
- NestJS backend integrates with OpenWeather.
- OpenWeather responses are normalized into internal application models.
- Weather providers are abstracted behind a WeatherProvider contract.
- Provider-specific mapping is isolated inside provider implementations.
- Weather insights and recommendations are generated by backend business logic.

## Production Readiness

- The app emits structured, JSON-friendly logs for startup, HTTP requests, OpenWeather failures, invalid locations, and unexpected backend errors.
- HTTP request logs are emitted after each response finishes and include method, path, status code, duration, request ID when present, and user agent when present.
- Logs intentionally avoid sensitive data. OpenWeather API keys are never logged.
- The backend uses an in-memory cache to reduce repeated external OpenWeather API calls for the same endpoint, normalized location, and units.
- Cached weather responses expire after 10 minutes by default. Override this with `WEATHER_CACHE_TTL_SECONDS=<seconds>`.
- For multi-instance production deployments, replace the in-memory cache with Redis or another distributed cache so instances share cached weather responses.
- In production, stdout/stderr logs should be shipped to Datadog, CloudWatch, Sentry, or another observability platform.
- Rate limiting is recommended before production to protect OpenWeather quota.

## Tradeoffs

- In-memory cache was intentionally chosen for simplicity during the challenge.
- OpenWeather integration uses direct REST calls instead of SDK wrappers.
- The backend is structured to support multiple weather providers later.
- Authentication was intentionally omitted to keep focus on API architecture and frontend experience.

## Project Notes

- The backend normalizes OpenWeather responses before returning them to the frontend.
- The frontend keeps server state in TanStack Query and avoids global state libraries.
- API calls are isolated in `frontend/src/api`.
- Backend response types are mirrored in `frontend/src/features/weather/types`.
- Forecast is requested from `/weather/forecast` and rendered below current weather when available.
- Business recommendations are generated by the backend and displayed by the frontend.
- `WeatherProvider` is an interface-style provider token, so OpenWeather can be replaced later.
- `OpenWeatherMapper` translates OpenWeather payloads into normalized internal weather models.
- `HttpExceptionFilter` centralizes error response shape.
